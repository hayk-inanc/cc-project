# SPRINT-03 — Change request: не терять картину при сбое (релиз R4)

Третья неделя, занятие 6. Изменение требований заказчика к US-06 и US-07 плюс закрытие US-10. Правила R2 и R3 действуют там, где не изменены здесь.

---

## Письмо заказчика № 3

> Преподаватели попробовали программу на занятиях. Одна жалоба, зато от всех: нажимаешь кнопку посреди объяснения, источник не отвечает — и карта пустеет. Суда, которые только что разбирали с курсантами, исчезают, и приходится обновлять страницу.
>
> Просим изменить поведение: если новая попытка не удалась или ничего не принесла, оставить на карте то, что было, и отдельно показать, что попытка не удалась и когда. Заменять картинку только тогда, когда пришёл настоящий непустой результат. При этом ни в коем случае не выдавать старые данные за свежие — подпись должна честно говорить, что именно на карте и когда оно получено.
>
> Понимаем, что раньше мы сами просили показывать результат последней попытки. Это не ошибка исполнителя — это новое требование после опыта использования.
>
> И, как договаривались, ждём инструкцию по установке и запуску для второго ноутбука.

## Часть A. Что делаем

### Согласованные значения

Два независимых состояния: **показанный набор** с подписью источника и **результат последней попытки** — отдельная строка.

- До первого нажатия строка результата попытки не показывается. Отдельных сообщений о пустом результате и ошибке под подписью источника больше нет — только строка результата попытки.
- Во время запроса показанный набор остаётся на карте; демонстрация продолжает движение. Кнопка заблокирована; результат попытки — «Загрузка…».
- Ошибка или пустой ответ не меняют набор и подпись источника. Результат попытки: «Попытка HH:MM:SS UTC: за время сбора позиции не получены» (время — `collectedAt` из ответа) или «Попытка HH:MM:SS UTC: не удалось получить данные: <message>» (время — `attemptedAt` из ответа). Если ответа нет или тело не разобрано — «Попытка: не удалось получить данные: Нет ответа сервера», без времени; набор не меняется.
- Только непустой успех атомарно заменяет набор, обновляет подпись источника (формат прежний: «AISStream · снимок за 15 с · получен HH:MM:SS UTC · судов: N · выборка неполная»), показывает «Попытка HH:MM:SS UTC: получено судов: N» и останавливает демодвижение. Выбранный `id` есть в новом наборе — карточка обновляется; нет — выбор снимается, карточка закрывается.
- Возврат карты к начальному виду при первом непустом успехе сохраняется.
- Наборы разных загрузок не сливаются. Отсутствие судна в новом наборе не трактуется как уход из района.
- Предыдущий набор есть всегда: после загрузки страницы это демонстрация. Нажатие без ключа оставляет демонстрацию с подписью «Демонстрационные данные», в строке результата — «Попытка HH:MM:SS UTC: не удалось получить данные: Ключ AISStream не настроен».
- Постоянная подсказка на экране: «После обновления страницы снова показываются демонстрационные данные».
- Все времена интерфейс берёт из тел ответов сервера, не из браузерных часов.
- Порядок панели сверху вниз: кнопка, подпись источника, строка результата попытки, подсказка, карточка.

### Задачи

**B-18. Интерфейс R4.** Состояния и тексты выше. Критерий: сценарии ниже проходят вручную; блокировка кнопки и возврат карты сохранены.

**B-19. Тесты контракта R4** (браузер, подмена ответа `GET /api/snapshot`; все времена — из тел ответов):

- успех с `collectedAt` 12:00:00 → набор заменён, подпись содержит «получен 12:00:00 UTC», строка «Попытка 12:00:00 UTC: получено судов: N», демодвижение остановлено;
- повторное ожидание → предыдущий набор на карте, кнопка заблокирована, строка «Загрузка…»;
- пустой ответ с `collectedAt` 12:01:00 после успеха 12:00:00 → подпись «получен 12:00:00 UTC» сохранена, строка «Попытка 12:01:00 UTC: за время сбора позиции не получены»;
- ошибка с `attemptedAt` 12:01:00 после успеха 12:00:00 → набор и подпись сохранены, строка «Попытка 12:01:00 UTC: не удалось получить данные: …»;
- ошибка при демонстрации → суда движутся, подпись «Демонстрационные данные», строка результата видна;
- выбранное судно отсутствует в новом наборе → карточка закрыта; присутствует → карточка показывает новые координаты и время;
- судно с `speedKnots: null` и `courseDeg: null` → «Нет данных» в обоих полях, `data-icon="neutral"`;
- успех с `truncated: true` → подпись заканчивается на « · остановлено на лимите 100»;
- второй непустой успех после сдвига карты → центр и масштаб не изменились;
- после непустого успеха продвижение `page.clock` на несколько тиков не меняет координаты настоящих судов;
- ответ без тела → «Попытка: не удалось получить данные: Нет ответа сервера», набор сохранён;
- подсказка об обновлении страницы присутствует.

Критерий: все случаи зелёные; из старых тестов изменены только тесты состояний R2 из B-16 (ошибка и пустой ответ — теперь набор сохраняется), список изменённых назван; тесты движения и выбора без правок.

**B-20. Финальная приёмка.**

- Все тесты зелёные; `tsc --noEmit` чист; `next build` проходит.
- Без ключа: демонстрация работает, сборка проходит, нажатие оставляет демонстрацию и показывает результат попытки с текстом «Ключ AISStream не настроен».
- С ключом: одна ручная успешная загрузка зафиксирована с временем и количеством судов — или зафиксирована недоступность источника.
- `git ls-files` не содержит `.env.local`; значение ключа не находится поиском по рабочей копии, `.next/static` и содержимому архива checkpoint.
- Каждая команда из README выполнена и дала описанный результат.

**B-21. README.** Запуск, переменные без значений, команды проверок, «снимок, а не мониторинг», правило сохранения набора при сбое, известные ограничения. Критерий: каждая команда README выполнена и дала описанный результат; слов «мониторинг» и «все суда района» нет.

### Результат занятия

Последняя проверенная картина не теряется при сбое и не выдаётся за свежую. Приёмка и сборка пройдены, README написан, checkpoint 06: запись, коммит, архив. Это финальное состояние проекта.

### Чего не делаем

Автоматическое обновление по таймеру; история снимков; сравнение старого и нового набора; пометка «ушедших» судов; сохранение набора между обновлениями страницы. Если на прошлых неделях более сильное поведение уже реализовано и принято — оно не ухудшается; проверяется соответствие сценариям выше.

## Часть B. Как делаем с Claude Code

Здесь «мы» — тот, кто ведёт агента: на занятии это ментор, при повторении в своей копии — вы.

### Метод недели

Изменение требований к уже принятому поведению. Задача агенту — не «починить баг», а изменить модель состояния, не переписывая интеграцию и отображение. Проверка изменения — регрессия: тесты состояний R2 из B-16 («ошибка → судов нет», «пустой ответ → судов нет») обязаны покраснеть и быть переписаны; тесты движения и выбора обязаны остаться зелёными. Если покраснели не те — изменение вышло за границы.

### Порядок работы

**Постановка.** Агент читает письмо и задание, сверяет checkpoint 05, исследует текущие состояния загрузки и предлагает минимальный план: два состояния вместо одного. Следим за формулировкой: прежнее поведение — согласованное правило, не баг. Агент, который начинает с «исправим ошибку», заложит неправильную рамку.

**Реализация (B-18).** Один запрос с полным контрактом из части A: тексты литералами, источник времени — из тел ответов, поведение карточки по наличию `id`, сохранение блокировки и возврата карты. Ловушки: наборы сливаются; подпись источника обновляется на время неудачной попытки; демодвижение останавливается при нажатии (старое поведение); карточка показывает данные старого набора после замены.

**Тесты (B-19).** Подмена ответа собственного endpoint — это доказывает поведение интерфейса, не доступность AISStream. Времена — литералами из тел подменённых ответов; движение и остановку демонстрации проверяем продвижением `page.clock`, без `waitForTimeout`. Требуем от агента список изменённых старых тестов с объяснением: тесты состояний R2 из B-16 обязаны упасть и быть переписаны под новый контракт; тесты движения и выбора — остаться без правок.

**Приёмка (B-20).** Агент: полный прогон — тесты, типы, сборка. Руками, не через агента: убрать `.env.local`, перезапустить, нажать кнопку — демонстрация на месте, строка результата с текстом об отсутствии ключа; поиск значения ключа по рабочей копии, `.next/static` и архиву checkpoint; вернуть ключ, нажать — результат записывается с временем и количеством судов или как недоступность.

**README (B-21).** Команды проверок в README — те же, что уже выполнены в приёмке; их вывод прилагается. README не обещает мониторинг и полноту: «снимок на момент нажатия», «выборка неполная».

**Checkpoint 06.** Финальный: проверки, ограничения, статус живого источника, отклонения от задания за весь блок.

### Примеры запросов

- «Прочитай docs/tasks/SPRINT-03b-CHANGE-REQUEST.md, сверь docs/checkpoints/CHECKPOINT-05.md с кодом, исследуй текущие состояния загрузки. Предложи минимальный план: показанный набор и результат последней попытки как отдельные состояния. Прежнее поведение багом не называй.»
- «Реализуй правило из задания: при ожидании, ошибке и пустом ответе набор и подпись сохраняются, демонстрация продолжает движение; отдельной строкой — результат попытки с текстами и источником времени из задания. Только непустой успех заменяет набор. Карточка — по наличию id в новом наборе. Блокировку кнопки и возврат карты сохрани.»
- «Добавь браузерные тесты с подменой ответа /api/snapshot по списку из задания; времена — из тел ответов, ожидания литералами. Старые тесты меняй только там, где изменился контракт, и назови, какие и почему.»
- «Запусти все тесты, tsc --noEmit и next build. Покажи вывод.» Дальше — руками, без агента: проверка без ключа и поиск значения ключа.

### Что вы должны понять к концу занятия

- Почему одно состояние «данные на карте» ломается на первом же сбое.
- Какие старые тесты покраснели и почему это правильно.
- Почему демонстрация при сбое остаётся демонстрацией и не помечается как настоящие данные.
- Что в финальном результате доказано тестами, что — ручным подключением, что — не доказано.
